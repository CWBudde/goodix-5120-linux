# Plan: next steps for `27c6:5120`

Written 2026-09-19, condensed 2026-09-20. Read [`FINDINGS.md`](FINDINGS.md) first: the first live run
(2026-08-17) wedged the ITE embedded controller and killed the internal keyboard until a cold power
cycle.

The phases are ordered by risk. Phases 1–3 never touch the device. Phase 4 cannot start until its gate
is met.

**This file is the plan, not the record.** Every finding it used to restate now lives in
[`docs/protocol.md`](docs/protocol.md) (the wire protocol and every observed run),
[`docs/acpi.md`](docs/acpi.md), [`docs/windows-capture-runbook.md`](docs/windows-capture-runbook.md),
[`docs/bisect-runbook.md`](docs/bisect-runbook.md) and [`FINDINGS.md`](FINDINGS.md). Append new
observations there, not here.

---

## Where we stand (2026-09-20)

- **The protocol is known end to end up to `d0`.** Framing, the `0xb0` ACK convention and two transfers
  per command are confirmed against hardware; the vendor's 14-frame init is identical over 9 complete
  inits in the driver's own debug log. Since the 224-byte `0x90` config was recovered from `gfusb.dll`,
  **every outbound byte the vendor sends up to `d0` is in this repository.**
- **The device is an ITE EC** (`GF_ITE_EC_20063`) in front of a Goodix sensor, chip ID `0x2504`,
  80 × 64. The vendor driver treats it as an "EC project": no `nop`, and no firmware update, ever.
- **Cause of the wedge, confirmed:** `0xe4` sent **without its 8-byte argument**. Run 4 sent that one
  frame and nothing else, and the keyboard died. The code can no longer build it.
- **The EC tolerates the host going away.** The vendor driver sends nothing on idle or D0Exit and
  leaves the EC armed in FDT-down mode with TLS up — which is also what Run 1's unsolicited `0x32` was.
- **The PSK is the one remaining obstacle.** 32 random bytes generated by the Windows driver, sealed
  with DPAPI in `Goodix_Cache.bin` and stored in the EC. Without it: everything up to `d0`, and not one
  image.

Open work, in order: **Phase 2** (publish — drafted, not posted), **Phase 4** (live plaintext runs, one
command per run), **Phase 5** (the PSK, then TLS and images).

## Phase 3 — Passive research — done, except one optional capture

Each item is written up in `docs/protocol.md` unless another file is named.

- [x] **Windows driver analysis** — `gfusb.dll` 1.1.122.127 (UMDF), from its strings and its ETW debug
      log; the driver package itself copied off the read-only Windows mount to `windows-driver/`
      (gitignored). Read at EVTX record level the log holds **17545 records, 2026-08-15 to 2026-09-19,
      18 inits of which 9 are complete** — not the "8 inits" that `strings -el` suggested, which cannot
      date a record.
- [x] **Windows USB capture, steady state** — a `WbioSrvc` restart plus a 43-capture session. No init on
      the wire, because a service restart does not reload the UMDF driver. Every checksum verifies.
- [x] **The 224-byte `0x90` config, recovered 2026-09-20** by static extraction from `gfusb.dll`, which
      holds it 19 times byte-identical; nothing executed. `cmd/goodix-probe/vendor.go` carries it as
      `uploadConfigPayload`, the replay fixture no longer substitutes synthetic bytes, and three tests
      pin it. **This was the last missing frame of the vendor init.** `0x90` stays out of `steps`:
      knowing the bytes is not permission to send them.
- [x] **PSK sealing, read-only** — `Goodix_Cache.bin` (332 bytes, written once in 2021) carries the
      DPAPI provider GUID in its header, so the PSK is sealed with `CryptProtectData`, not TPM and not
      SGX, whatever the `gf_sgx_seal_data` strings suggest. Recovering the plaintext needs the DPAPI
      master key, which is user- or machine-scoped — a separate question, and what Phase 5 turns on.
- [x] **ACPI tables**, read only, no method called: **nothing in ACPI can reset the EC or cut power to
      the sensor's USB port**, and the keyboard and the ACPI EC are separate host interfaces into the
      same ITE part — which is the shape of the keyboard incident. See [`docs/acpi.md`](docs/acpi.md),
      which also documents the EC refresh counter that replaced the useless SCI counter in `--bisect`.
- [x] **EC identity** — EC firmware release 1.8, BIOS 1.08, board `HVY-WXX9-PCB`.
- [x] **Keep the debug log from every Windows session.** It is circular (20 MB, 320 chunks) and has
      already wrapped, so re-copy it after every capture attempt: it is the only thing that says
      whether the init you were trying to catch actually ran. Read it with `cmd/goodix-evtx`, which
      withholds the OTP and the `0xe4` reply — **the log itself is secret-bearing**, and `captures/` is
      gitignored for that reason as much as for the biometrics.
- [ ] **Capture a real init on the wire** — *corroboration now, not a gate.* The `0x90` it was needed
      for has been recovered. Four attempts produced no init, and the reason is settled: **USBPcap does
      not follow the device across the PnP re-enumeration** that a full init requires, and the driver
      short-circuits any init that is merely a resume, so there is no gentler trigger. The procedure was
      right; the tool missed the result. What to do differently — and why Uninstall + "Scan for hardware
      changes" is a *worse* idea, not a fallback — is in
      [`docs/windows-capture-runbook.md`](docs/windows-capture-runbook.md). Still worth having for the
      log-versus-wire match byte for byte and the `d0` handshake as it actually appears.

## Phase 3b — Bisect the wedge — done (2026-09-19)

Runs 2, 3 and 4 located it: attach, `nop` and `0xa8` pass, and the **empty-payload `0xe4` wedges the EC
on its own** — one frame, no preconditions, ACK after 4 ms and then a dead keyboard. What is fatal is
the empty payload, not the opcode: the vendor sends `0xe4` with its 8-byte argument in all 9 complete
inits and gets ACK plus data. Nothing more is to be learned from that frame, and Phase 3c made it
unbuildable. All four runs are recorded in `docs/protocol.md`; the procedure is in
[`docs/bisect-runbook.md`](docs/bisect-runbook.md).

## Phase 3c — Align the code with the vendor sequence — done (2026-09-19)

`cmd/goodix-probe/vendor.go` holds the vendor's 14-frame init and is the single source of truth for
every payload in the binary; default `steps` is one command, `a8 [00 00]`. Every opcode carries a
`PayloadRule` as a *required* argument to `register`, enforced in `sender.Send` before a byte is
written, so **the frame that killed the keyboard can no longer be built** — including on `--allow-e4`,
which now sends the vendor's 8-byte argument. `ae` and `82` are `ClassSafe`, `98`/`d4`/`50`/`32`/`34`/`36`
`ClassStateChanging`; `0xd2` was deliberately **not** registered, appearing in neither the log nor either
capture. Replay fixtures cover the vendor init and the capture loop, with every remaining synthetic byte
inbound and named. `cmd/goodix-pcap` reads USBPcap captures offline and is structurally unable to reach
hardware, proven by purity tests. `CLAUDE.md` describes the resulting architecture; that description is
the current one.

## Phase 4 — Live runs (only if the gate is met)

**Gate:** Phase 3c complete (2026-09-19), **and** each planned command matches the vendor sequence byte
for byte, opcode *and* payload. Both halves are enforced in code rather than checked by hand:
`TestStepPayloadsMatchVendorInit` fails if a step is not a vendor frame, and `./goodix-probe --dry-run`
prints the probe's frames next to the whole vendor sequence for a human to compare.

Since 2026-09-20 the gate's *data* half is fully satisfied up to `d0`, the `0x90` config included.
Nothing about that loosens anything: the gate was never only about having the bytes.

Setup for every run:

- [ ] Plug in an external USB keyboard, or better, drive the machine over SSH from a second computer.
- [ ] Nothing else open or unsaved on the machine.
- [ ] Rehearse the recovery first: shut down fully, unplug the charger, hold the power button ~30 s.
      A warm reboot doesn't reset the EC.
- [ ] Use `--bisect` (keyboard check after each step). Drain responses before exiting.
- [ ] After each run, check that the internal keyboard still works
      (`evtest` on `AT Translated Set 2 keyboard`) and that `1-4` is still in
      `/sys/bus/usb/devices/`. Stop at the first sign of trouble.
- [ ] Append every run to `docs/protocol.md` as "Run N".

Proposed order, one new step per run, always in vendor order, prefix from the vendor sequence:

1. `a8 [00 00]` → expect ACK + `GF_ITE_EC_20063` (known safe with an empty payload).
2. `+ ae [55 + timestamp]` → expect 20-byte state, no ACK. Tells us whether TLS is still up from Windows.
3. `+ e4 [03 00 02 bb 00 00 00 00]` → expect ACK + 41 bytes. **This tests the wedge hypothesis.**
   Only with the external keyboard attached, and only after steps 1–2 passed twice.
4. `+ a2 [01 14]`, `82 [00 00 00 04 00]`, `a6 [00 00]` → reset, chip ID `0x2504`, OTP.
5. Stop there. `70`/`98`/`90` configure the sensor, and `d0` starts a handshake we can't finish without
   the PSK. What gates this step has nothing to do with missing bytes — it is live-hardware safety, one
   command per run, and the PSK question beyond `d0`.

**Never, under any circumstances:** run upstream's `driver_51x0.main()` or any IAP/firmware-write path.
It would try to flash `GF_ST411SEC_APP_12117.bin` onto the ITE EC that also runs the keyboard.
`write_firmware` (`0xf0`) and `preset_psk_write` (`0xe0`) stay out of the binary.

## Phase 5 — Driver work (far future, conditional)

Blocked on the PSK. The options, in order of preference:

1. **Unseal the Windows PSK** from `Goodix_Cache.bin`, if the DPAPI master key can be derived on Linux.
   Non-destructive, and Windows Hello keeps working.
2. **Read it out of a running Windows** — the driver's memory, or its debug switches
   (`psk_simulation_switch`, `Local_test_original_psk`). Local analysis only.
3. **Provision our own PSK with `0xe0`.** Destructive: it overwrites the EC's PSK and breaks Windows
   Hello until Windows re-provisions it. Last resort only, behind an explicit build tag, and only after
   checking that the Windows driver re-provisions cleanly.

Then:

- TLS server side in `internal/tlspsk`: the host is the **server**, suite `0x00ae`. Check whether
  `openssl s_server -psk` offers `PSK-AES128-CBC-SHA256`.
- Image decode for 80 × 64 (`internal/image`). The 12-bit packing from upstream is a hypothesis for this
  sensor. **7744 is the TLS *record* length, not the plaintext** — the plaintext is 7680–7695 bytes; see
  `docs/protocol.md`, "How big is an image, really". It has to be measured, but the arithmetic already
  corroborates 80 × 64.
- FDT loop (`32`/`20`/`34`) for finger detection, then a libfprint driver or a TOD module, developed
  together with upstream.
